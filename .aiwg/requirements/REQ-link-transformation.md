# Requirements Document: Internal Link Transformation

**Document ID**: REQ-LINK-TRANSFORM-001
**Created**: 2025-12-03
**Status**: Draft
**Priority**: High
**Stakeholders**: Development Team, Content Authors, Tenant Operators

---

## Executive Summary

Pagenary currently does not transform Markdown-style internal links (`[text](./file.md)`) into hash-based navigation links that the SPA router understands. This breaks navigation between documents in tenant content, forcing users to manually edit URLs or use the left navigation panel. This requirement defines the complete link transformation system needed to enable seamless cross-document navigation within tenant documentation.

The solution must transform relative file paths to section IDs during the Markdown-to-HTML conversion process in the build pipeline, accounting for nested directory structures, multiple content organization patterns, and various link formats.

---

## Problem Statement

### Current Behavior

When a Markdown document contains internal links:

```markdown
[Get Started](./quick-start.md)
[Technical Details](../technical/whitepaper.md)
[System Overview](system-overview.md)
```

These are currently converted to anchor tags with literal file paths:

```html
<a href="./quick-start.md">Get Started</a>
<a href="../technical/whitepaper.md">Technical Details</a>
<a href="system-overview.md">System Overview</a>
```

**Impact**:
- Clicking these links attempts to navigate to non-existent files
- Browser shows 404 errors
- Navigation breaks user experience
- Content authors must manually construct hash URLs
- Defeats the purpose of Markdown convenience

### Expected Behavior

Links should be transformed to hash-based navigation:

```html
<a href="#getting-started/quick-start">Get Started</a>
<a href="#technical/whitepaper">Technical Details</a>
<a href="#system-overview">System Overview</a>
```

When clicked, these trigger the SPA router to:
1. Load the appropriate section module
2. Update the left navigation to show the active section
3. Expand parent groups if necessary
4. Scroll to top of content area

## Functional Requirements

### FR-001: Relative Path Resolution

**Priority**: Critical

**Description**: Transform relative Markdown links to section IDs by resolving the target file path relative to the source document's location in the content tree.

**Acceptance Criteria**:
- [ ] Same-directory links (`./file.md`, `file.md`) resolve to sibling section IDs
- [ ] Parent-directory links (`../file.md`) traverse up the content tree
- [ ] Multi-level traversal (`../../other/file.md`) correctly resolves across nested structures
- [ ] Index files (`./index.md`, `../index.md`) resolve to parent directory section ID
- [ ] Resolution respects content root boundaries (flat `content/`, nested root, or tenant root)

**Examples**:

Source: `tenants/alpha/getting-started/quick-start.md`

| Markdown Link | Resolved Section ID |
|---------------|---------------------|
| `[Intro](./introduction.md)` | `getting-started/introduction` |
| `[Overview](../overview.md)` | `overview` |
| `[Whitepaper](../technical/whitepaper.md)` | `technical/whitepaper` |
| `[Index](./index.md)` | `getting-started` |
| `[Home](index.md)` | `getting-started` |

**Edge Cases**:
- Links to files outside content root (should remain unchanged or emit warning)
- Links with URL-encoded characters
- Links with spaces in filenames
- Case-sensitive vs case-insensitive filesystems

---

### FR-002: Section ID Derivation

**Priority**: Critical

**Description**: Derive target section IDs using the same algorithm as the build process to ensure consistency between file paths and generated section IDs.

**Acceptance Criteria**:
- [ ] Section IDs match those in `manifest.js` generated by build process
- [ ] Supports nested directory structure (e.g., `parent/child/grandchild`)
- [ ] Handles flat content directory structure (`content/file.md` → `file`)
- [ ] Respects `_manifest.json` section ID overrides
- [ ] Strips file extensions (`.md`, `.html`, `.js`) from IDs
- [ ] Uses directory name for `index.md` files

**Algorithm** (from `build-tenants.js`):

```javascript
function deriveSectionId(parentId, name, isIndex = false) {
  const stem = name.replace(/\.[^.]+$/, ''); // Strip extension

  if (isIndex || stem === 'index') {
    // index.md resolves to parent directory ID
    return parentId || stem;
  }

  if (parentId) {
    return `${parentId}/${stem}`;
  }
  return stem;
}
```

### FR-003: External Link Preservation

**Priority**: Critical

**Description**: Preserve external links (HTTP, HTTPS, mailto, etc.) without modification.

**Acceptance Criteria**:
- [ ] HTTP/HTTPS URLs remain unchanged
- [ ] `mailto:` links remain unchanged
- [ ] `tel:` links remain unchanged
- [ ] Protocol-relative URLs (`//example.com`) remain unchanged
- [ ] Fragment-only links (`#section`) remain unchanged (already hash-based)
- [ ] Absolute paths to non-content resources remain unchanged

**Examples**:

| Markdown Link | Result |
|---------------|--------|
| `[Docs](https://example.com/docs)` | `href="https://example.com/docs"` |
| `[Email](mailto:support@example.com)` | `href="mailto:support@example.com"` |
| `[Call](tel:+1-555-1234)` | `href="tel:+1-555-1234"` |
| `[Section](#top)` | `href="#top"` (unchanged) |

### FR-004: Anchor Fragment Support

**Priority**: High

**Description**: Support Markdown links with anchor fragments that navigate to specific headings within target documents.

**Acceptance Criteria**:
- [ ] Links like `[text](./doc.md#section)` transform to `#doc-id#section`
- [ ] Fragment-only links (`#heading`) remain unchanged
- [ ] Fragments are preserved during path resolution
- [ ] Invalid fragments do not break link transformation

**Examples**:

| Markdown Link | Resolved Link |
|---------------|---------------|
| `[API Auth](./api.md#authentication)` | `#developers/api-reference#authentication` |
| `[Top](#overview)` | `#overview` (unchanged) |
| `[External](https://ex.com#top)` | `https://ex.com#top` (unchanged) |

**Note**: Current SPA router does not scroll to anchor fragments. This requirement lays groundwork for future enhancement (FR-009).

### FR-005: Build-Time Transformation

**Priority**: Critical

**Description**: Perform link transformation during the build process in `build-tenants.js`, not at runtime in the browser.

**Acceptance Criteria**:
- [ ] Transformation occurs in `parseInlineMarkdown()` or `markdownToHtml()` functions
- [ ] Transformed links are embedded in generated `.js` modules
- [ ] No runtime link processing required in `app.js`
- [ ] Supports all content types: `.md`, `.html`, and `.js` modules (for consistency)

**Rationale**:
- Build-time transformation enables link validation
- Reduces runtime overhead
- Allows dead link detection during CI/CD
- Enables static analysis of content graph

### FR-006: Link Validation and Error Handling

**Priority**: High

**Description**: Validate transformed links and provide warnings for broken references during build.

**Acceptance Criteria**:
- [ ] Warn when link target file does not exist in content tree
- [ ] Warn when target file exists but generates no section (excluded, invalid format)
- [ ] Preserve original link on validation failure (graceful degradation)
- [ ] Emit structured warnings with source file, line number (if available), and target
- [ ] Do not fail build on broken links (warning only)
- [ ] Optionally fail build with `--strict-links` flag

**Warning Format**:

```
[WARN] tenant-alpha/getting-started/quick-start.md
  ↳ broken link: [Missing](../nonexistent.md)
  ↳ target not found in content tree
  ↳ preserving original link for manual review
```

### FR-007: Content Root Discovery

**Priority**: Critical

**Description**: Automatically detect content root type (flat, nested, root-level) and apply appropriate path resolution logic.

**Acceptance Criteria**:
- [ ] Correctly identifies flat structure (`content/` subdirectory)
- [ ] Correctly identifies nested structure (subdirectories with content)
- [ ] Correctly identifies root-level structure (content files in tenant root)

**Content Root Types** (from ADR-010):

### FR-010: Relative Path Normalization

**Priority**: High

**Description**: Normalize relative paths to handle variations in link syntax.

**Acceptance Criteria**:
- [ ] `./file.md` and `file.md` are treated identically (same directory)
- [ ] `../file.md` and `./../file.md` are treated identically (parent directory)
- [ ] Trailing slashes in directory links are handled gracefully
- [ ] Double-slash (`//`) in paths are normalized to single slash
- [ ] Backslashes (`\`) are converted to forward slashes (Windows compatibility)

**Examples**:

| Input Link | Normalized |
|------------|------------|
| `./dir/file.md` | `dir/file.md` |
| `.//dir//file.md` | `dir/file.md` |
| `dir\file.md` | `dir/file.md` |
| `dir/../file.md` | `file.md` |

**Input**:

**Output**:

### Integration Points

**Modified Functions** (in `build-tenants.js`):

1. **`parseInlineMarkdown(input, context)`**
   - Add `context` parameter with source path and content tree info
   - Call `transformLink(href, context)` for each link
   - Return transformed HTML

2. **`transformLink(href, context)`** (new function)
   - Classify link type (external, internal, fragment-only)
   - Resolve relative path to section ID
   - Validate target exists (optional warning)
   - Return transformed href or original on failure

3. **`ensureMarkdownModule(sourcePath, targetPath, context)`**
   - Pass transformation context to `markdownToHtml()`

4. **`buildSectionIdMap(contentRoot, manifest)`** (new function)
   - Build map from file paths to section IDs
   - Used for link validation and transformation

**Integration with Router**:
- No changes required to `app.js` or `router.js`
- Transformed links use existing hash-based routing
- SPA router already handles `#section-id` navigation

### Algorithm: Link Transformation

**Pseudocode**:

```javascript
function transformLink(href, context) {
  // 1. Classify link type
  if (isExternalLink(href)) {
    return href; // Preserve external links
  }

  if (isFragmentOnly(href)) {
    return href; // Preserve fragment-only links
  }

  // 2. Parse path and fragment
  const [path, fragment] = href.split('#');

  // 3. Normalize relative path
  const normalizedPath = normalizePath(path);

  // 4. Resolve relative to source file
  const sourcePath = context.sourcePath;
  const sourceDir = path.dirname(sourcePath);
  const absolutePath = path.resolve(sourceDir, normalizedPath);

  // 5. Convert absolute content path to section ID
  const sectionId = deriveSecti onId(absolutePath, context);

  // 6. Validate section exists (optional)
  if (!context.sectionIdMap.has(sectionId)) {
    console.warn(`Broken link: ${href} in ${sourcePath}`);
    return href; // Fallback to original
  }

  // 7. Construct hash-based href
  let transformedHref = `#${sectionId}`;
  if (fragment) {
    transformedHref += `#${fragment}`;
  }

  return transformedHref;
}

function isExternalLink(href) {
  return /^(https?:|mailto:|tel:|\/\/)/.test(href);
}

function isFragmentOnly(href) {
  return href.startsWith('#');
}

function normalizePath(path) {
  return path
    .replace(/\\/g, '/') // Windows backslashes
    .replace(/\/+/g, '/') // Multiple slashes
    .replace(/^\.\//, '') // Leading ./
    .replace(/\/\.$/, ''); // Trailing /.
}

function deriveSectionId(absolutePath, context) {
  // Strip content root prefix
  const relativePath = path.relative(context.contentRoot, absolutePath);

  // Strip extension
  const stem = relativePath.replace(/\.[^.]+$/, '');

  // Handle index files
  if (stem.endsWith('/index') || stem === 'index') {
    return path.dirname(stem);
  }

  // Convert slashes to section ID format
  return stem.replace(/\\/g, '/');
}
```

## Assumptions and Constraints

### Assumptions

1. **Content files use standard Markdown link syntax**: `[label](path)` format.
2. **Section IDs are stable**: Renaming files requires updating links (no auto-refactoring).
3. **Build process has read access to entire content tree**: Needed for validation.
4. **Content tree structure is available during Markdown processing**: Requires passing context through pipeline.
5. **No circular link references**: Not validated, but SPA router handles this gracefully.

**Impact if Invalid**:
- Non-standard link syntax: Links not transformed, remain broken.
- Unstable section IDs: Frequent link breakage, manual updates required.
- Limited content tree access: Cannot validate links, must skip validation step.

---

### Constraints

1. **No changes to SPA router**: Link transformation must work with existing hash-based routing.
2. **No runtime link processing**: All transformation at build time for performance.
3. **Backward compatibility**: Existing tenants continue to work without modification.
4. **No new npm dependencies**: Keep build process lightweight.
5. **Build process must remain fast**: <5% performance impact acceptable.

**Technical Constraints**:
- JavaScript regex for link parsing (no AST parser for Markdown)
- Node.js path resolution (cross-platform compatibility required)
- Build process runs in single-threaded Node.js (no parallelization)

**Business Constraints**:
- Must not break existing tenant deployments
- No changes to tenant content format (remains standard Markdown)
- No additional author training required
